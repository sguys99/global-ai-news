# Phase 7-5 Lighthouse(모바일) — 영어 홈·기사 SEO 100, 성능 저하 확인 (2026-11-06)

> 체크리스트 항목: "Lighthouse(모바일) 영어 홈·기사 SEO 점수 100, 성능 저하가 없는지 확인한다."

## 결론

- **SEO 100: 통과.** 영어 홈·호·기사(해외 매체·한국 매체)·검색 5쪽 모두 3회 전부 SEO 100이다. 접근성·권장사항도 100이고, 실패한 감사 항목은 없다. 한국어 대응 페이지 5쪽도 네 범주 모두 100이다.
- **성능 저하: 영어판 때문에 생긴 저하는 없다.** 하나만 예외인데, 브라우저 언어에 `ko`가 없는 방문자에게 한국어 페이지에서 **CLS 0 → 0.051**이 생긴다. 원인은 영어 안내 줄(`EnglishNotice`)이 마운트 뒤에 끼어드는 것이다. 0.1 미만이라 "좋음" 구간이고, 한국어 브라우저에서는 0이다. 나머지 지표(FCP·LCP·TBT·바이트)의 출시 전후 차이는 실행 간 편차 안에 든다.
- **영어 페이지 성능은 대응하는 한국어 페이지와 같거나 낫다.** 영어 페이지는 한글 Hahmlet 조각을 받지 않아 약 400KB 가볍고, FCP는 1.7~1.8초로 한국어 2.1~3.9초보다 빠르다.
- **두 언어 공통으로 성능 점수가 50~70점대에 머무는 원인은 따로 있다.** 출시 전부터 있던 문제로, `PretendardVariable.woff2`(2.0MB)를 모든 페이지가 선로딩한다. 이 파일 하나만 막아도 영어 홈 LCP가 12.7초에서 2.7초로, 성능 점수가 58점에서 84점으로 오른다(아래 §5). 고칠 것을 권고한다(이번 범위에서는 고치지 않음).

읽는 법:

- **영어 vs 한국어.** 영어 페이지가 모든 쌍에서 같거나 낫다. 한국어 페이지는 한글 Hahmlet `unicode-range` 조각(약 31~49KB짜리 9~10개, 합계 약 400KB)을 더 받아 전송량이 많고 FCP가 늦다. 영어 한국 매체 기사(1392)는 `lang="ko"` 원제 줄 때문에 같은 조각을 받으므로 한국어판과 비슷하다(설계대로다).
- **TBT** 차이(한국어 검색 1,062ms 등)는 회차 사이 편차가 크다(같은 페이지에서 250ms에서 1,350ms까지 나옴). 언어 간 차이로 읽지 않는다.

## 4. 출시 전후 비교 — 한국어 페이지 (로컬 정적 서빙)

같은 `data/app.db`(sha256 `1a239717…`)로 Docker에서 빌드한 두 산출물을 비교했다. 출시 전 `data/regress/out-p7-base`(커밋 `232bbfc`)와 출시 후 `data/regress/out-p7`(커밋 `c024ced`, 영어판 병합)이다. 둘 다 `python3 -m http.server`로 `/global-ai-news/` 아래에서 서빙하고, 같은 설정으로 번갈아 3회씩 돌렸다. 로컬 서버는 gzip을 하지 않아 전송량이 크게 나오므로 공개 사이트 수치와 직접 비교하지 않는다. 출시 전후 두 빌드끼리만 비교한다.

판정:

- **FCP·LCP·Speed Index는 출시 전후 ±0.2초 안이다.** 페이지 크기는 비압축 기준 +22~23KiB(약 0.7%)로, hreflang 두 줄·`EN` 링크·셸 섬의 언어 전환 코드다.
- **TBT·성능 점수에는 일정한 방향이 없다.** 브라우저 언어가 `en-US`이면 출시 후가 조금 나쁘고 `ko-KR`이면 출시 후가 낫다. 같은 빌드 안의 편차(예: 출시 전 홈 TBT 247~1,348ms)가 전후 차이보다 커서 **저하로 보지 않는다.**
- **CLS 0 → 0.051은 실제 변화다.** `en-US`일 때 출시 후 한국어 페이지에서만 생기고(회차의 약 절반 이상), `ko-KR`일 때는 0이다. Lighthouse가 지목한 이동 요소는 헤더 아래 본문 `body.sh-body > div.flex-1` 전체(top 98px)다. 마운트 뒤 그 위에 끼어드는 영어 안내 줄 `EnglishNotice`(`src/components/EnglishNotice.tsx`, `sh-rie`)가 본문을 한 줄 밀어낸다. 공개 사이트의 한국어 기사 1392는 CLS 0.078인데, 여기에 웹 폰트 교체 몫(Lighthouse 원인 "Web font")이 더해진 값이다.

## 5. 두 언어 공통 성능 병목 — Pretendard 2MB 선로딩 (출시 전부터 있음)

- `src/app/fonts.ts`의 `localFont({ src: "../../public/fonts/PretendardVariable.woff2" })`는 next/font 기본값 `preload: true`를 따른다. 그래서 모든 페이지 `<head>`에 `ff840cfebfb63b0c-s.p.woff2`(전송 2,011KiB, 우선순위 High)가 선로딩된다. 이 파일이 페이지 전송량의 85~90%를 차지한다.
- 관측 LCP(약 1.4초)가 이 폰트 다운로드가 끝난 뒤(약 0.8초)에 찍힌다. 그래서 Lighthouse 시뮬레이션은 2MB를 1.6Mbps로 다시 계산하고, LCP 분해에서 "Render Delay"가 94%(약 12초)로 나온다.
- **확인 실험(공개 사이트, 1회, `--blocked-url-patterns='*ff840cfebfb63b0c*'`):**

| 페이지    | 성능    | FCP        | LCP             | 전송량         |
| --------- | ------- | ---------- | --------------- | -------------- |
| 영어 홈   | 58 → 84 | 1.7 → 1.8s | **12.7 → 2.7s** | 2,294 → 283KiB |
| 한국어 홈 | 53 → 67 | 3.9 → 2.7s | **14.9 → 4.5s** | 2,693 → 682KiB |

- 출시 전 빌드도 같은 파일을 같은 방식으로 받는다(§4 크기 참고). 따라서 영어판이 만든 저하가 아니다. 다만 영어 페이지는 한글 글리프가 거의 필요 없는데도(`lang="ko"` 원제 줄만 쓴다) 2MB 한글 폰트를 받는다.
