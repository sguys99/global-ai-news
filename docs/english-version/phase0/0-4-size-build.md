## 4. 한도와 추정

### GitHub Pages 한도(공식 문서 확인)

- 게시된 사이트는 **1 GB를 넘을 수 없다**("Published GitHub Pages sites may be no larger than 1 GB").
- 배포는 **10분**이 지나면 타임아웃된다(`deploy-pages` `timeout` 기본값 600000 ms).
- 대역폭은 월 100 GB 소프트 한도다. 빌드 시간당 10회 한도는 Actions 커스텀 워크플로에는 적용되지 않는다.
- `upload-pages-artifact`: 1 GB를 넘으면 "deployment might fail" 경고가 나온다. 비공식 절대 상한은 10 GB다.
- 파일 수 한도는 문서에 없다.
- 출처: [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [actions/deploy-pages](https://github.com/actions/deploy-pages), upload-pages-artifact README(검색 결과 인용).

### 모델

크기 S(t) = 공용 7 MB + 언어 수 × [기사 수 N(t) × p + 호 수 E(t) × e + og 호 + og 기사 창 7.4 MB + 고정 0.75 MB + N(t) × 1.51 KB(색인)].
N(t) = 1,232 + 26.8 t, E(t) = 32 + t. t는 2026-11-03부터 센 날 수다.
매 배포가 사이트 전체를 다시 빌드하므로 **페이지를 줄이면 지난 기사에도 곧바로 적용된다.** 크기는 누적 이력이 아니라 "기사 수 × 현재 페이지 크기"로 정해진다.

### 결론: 페이지 크기 목표 하나로는 "2년간 700 MB 이하"를 맞출 수 없다

- 단일 등급(모든 기사를 같은 크기로 낼 때) 역산: 2029-01-01(영어판 출시 약 2개월 뒤부터 2년)까지 한국어+영어 700 MB 이하가 되려면 **기사 페이지가 8 KB(호 150 KB) ~ 9.8 KB(호 100 KB) 이하**여야 한다. 이 시점 기사는 약 22,400건 × 2언어 = 44,800쪽이다. 지금 구조(Next RSC + React 셸)로는 `<head>` 4.4 KB와 루트 트리 4.9 KB만으로 이미 넘는다. 불가능하다.

### 제안하는 Phase 4 목표

**1단계 — 영어판 출시 전 필수(시나리오 C의 숫자)**

1. 기사 페이지 1건(HTML + `.txt`) **≤ 40 KB**(현행 92 KB → −57%). 수단:
   - 반복 카드의 긴 Tailwind 클래스 묶음을 짧은 컴포넌트 클래스로 바꾼다(`globals.css` `@apply`). class 문자열은 페이지 전체의 약 35 KB(HTML 11.8 + 인라인 RSC 약 12.5 + `.txt` 약 11)이고, 60%를 줄이면 약 −21 KB다.
   - 관련 기사 카드를 목록용 최소 필드·최소 마크업으로 바꾼다(약 25 KB → 12 KB, −13 KB).
   - 원문 발췌·다른 매체 목록의 상한을 둔다.
   - 그래도 모자라면 기사 페이지의 `index.txt`를 지운다(빌드 후처리 + 기사 링크 `prefetch={false}`, 404가 나면 Next가 전체 페이지 이동으로 넘어간다). 이것만으로 −30%다.
2. 호 페이지 **≤ 150 KB**(현행 365 KB). 마크업의 65%가 class 속성이라 1번과 같은 수단이 가장 잘 듣는다.
3. og 호 PNG는 **최근 30일만** 만든다(기사 PNG 7일 창과 같은 방식, 그 이전 호는 `og/default.png`). 그대로 두면 2년 뒤 약 100 MB다.
4. `deploy.yml` 크기 검사: 700 MB에서 `::warning::`, 950 MB에서 실패. 계획대로다.

**2단계 — 2년 목표를 위한 보관 등급(시나리오 D, 출시 후 6개월 안)**

- 게재 90일이 지난 기사는 **≤ 8 KB 라이트 페이지**로 낸다. RSC `.txt`와 인라인 flight, `_next` 스크립트 없이 정적 HTML로 만든다(제목·요약·원문 링크·canonical·hreflang·CSS 링크). 90일이 지난 호는 ≤ 40 KB(헤드라인 목록)로 낸다.
- 계산: 정착 후 증가 2 × (26.8 × 8 + 40 + 40.5) KB ≈ 0.59 MB/일. 최근 90일 전체 페이지는 2 × (90 × 26.8 × 40 KB + 90 × 150 KB) ≈ 220 MB로 일정하다. 2029-01-01에 693 MB, 1 GB는 2030-06이다.
- 창을 늘리면 라이트 페이지 허용치가 줄어든다. 창 180일이면 라이트 3.3 KB, 365일이면 0 KB여야 한다. 그래서 **90일 창 + 8 KB**가 현실적인 조합이다.
- 대안:
  - 보관 기사를 호 페이지 앵커로 합치고 `/article/<id>/`를 약 1.5 KB 리다이렉트 스텁으로 둔다. SEO상 기사별 canonical을 잃는다.
  - 호스팅을 옮긴다. Cloudflare Pages 무료 플랜은 파일 수 한도가 있다(20,000개, 확인 필요). 2년 뒤 한국어+영어 파일이 약 9만 개라 이 경우에도 별도 검토가 필요하다.

**별도 경고(크기 한도와 무관, 클라이언트 성능)**

- `search-index.json`·`feed-index.json`은 2년 뒤 언어당 gzip 5.3 MB / 3.4 MB가 된다. 월별 분할(shard) 또는 필드 축소가 필요하다.
- 1단계와 2단계 모두에서 색인 증가분이 2년 뒤 약 68 MB(두 언어 합계)로, D의 693 MB 중 10%다.
- 사이트맵은 한국어+영어 URL이 5만 개에 가까워진다. 사이트맵 인덱스로 나눠야 한다.

## 5. 빌드 시간

`deploy.yml` 성공 29회(2026-10-15 ~ 11-03, 취소 1회 제외). 시간은 `startedAt`부터 `updatedAt`까지다.

| 지표                                     |       평균 |      최대 | 최소 |
| ---------------------------------------- | ---------: | --------: | ---: |
| 워크플로 전체(대기 포함)                 |  **115초** | **164초** | 87초 |
| 매일 수집 뒤 dispatch 배포만(19회)       |      113초 |     141초 |    — |
| build 잡                                 |     95.5초 |     124초 | 71초 |
| └ `npm ci`                               |     25.7초 |      44초 | 10초 |
| └ `npm run build`(prebuild + next build) | **54.2초** |      67초 | 35초 |
| └ upload-pages-artifact(압축 약 34 MB)   |      4.1초 |       6초 |  3초 |
| deploy 잡                                |     12.3초 |      34초 |  8초 |
| └ deploy-pages                           |      9.1초 |      32초 |  6초 |

단계별 예시(최근 41602797769, 11-03): `npm ci` 35초 · build 44초 · upload 4초 · deploy-pages 7초, 전체 118초.

- 10-31부터 `npm ci`가 평균 16초에서 40초로 늘었다(npm 캐시 미스나 의존성 변경으로 추정). build 단계는 50–57초로 그대로다.
- 로컬 Docker 빌드: `npm run build` 72.9초. 그중 정적 페이지 1,479개 생성이 약 24초, 컴파일 17초, lint·타입 검사 8초다.
- 영어판으로 페이지가 두 배가 되면 생성 시간 +25–50초, 업로드 +5초 정도로 본다. deploy-pages 10분 타임아웃과 build 잡 15분 제한까지는 여유가 크다. 크기 한도가 먼저 문제가 된다.
- 참고로 `collect.yml` 수집 회차(dispatch 10회)는 평균 536초, 중앙값 376초, 최대 1,755초(10-25, 배치 대기)다. schedule 백업 회차는 guard에서 7–10초에 끝난다.
